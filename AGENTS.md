# AGENTS.md

This file provides guidance to agents when working with code in this repository.

## Stack
Java 21, Spring Boot **4.1.2** (Spring Framework 7, Security 7, Hibernate 7, JUnit 6, Jackson 3), PostgreSQL 18, Maven, springdoc 3.2.0 (its parent is Boot 4.1.2). Design and phase plan were agreed in chat; implementation proceeds one phase at a time, each reviewed by the user before the next starts.

## Commands (Windows / PowerShell)
- `java` and `mvn` are on `PATH` and `JAVA_HOME` points at JDK 21. The build needs Java 21 (JDK 25 may also be installed); if `java -version` does not report 21, point `JAVA_HOME` at a JDK 21 before running Maven.
- Unit tests only (no DB needed): `mvn -B -ntp test`
- **Single test class**: `mvn -B -ntp '-Dtest=GlobalExceptionHandlerTest' test`; single method: `'-Dtest=Class#method'`. **Quote every `-D...=...`** or PowerShell splits it and Maven fails with "Unknown lifecycle phase".
- Full build incl. integration tests: `mvn -B -ntp verify`
- Single integration test: `mvn -B -ntp '-Dit.test=BookwormApplicationIT' verify`. `*IT` classes run only under Failsafe (`verify`), never under `test`.
- Run the app: `mvn spring-boot:run '-Dspring-boot.run.profiles=dev'` (dev profile enables Swagger UI at `/swagger-ui.html` and loads the dev seed). Starting it applies pending Flyway migrations to `bookworm_db`. Only start it when the current phase's migrations are approved.
- Packaged jar (what was used to verify Phase 1): `mvn -B -ntp -DskipTests package`, then `Start-Process java -ArgumentList '-jar','target\bookworm-ecommerce-backend-0.0.1-SNAPSHOT.jar','--spring.profiles.active=dev'`. Background launches through the tool can exit silently; use `Start-Process` with redirected output and stop it afterwards.

## Database / secrets
- App needs `BOOKWORM_DB_USER`, `BOOKWORM_DB_PASSWORD` and `BOOKWORM_JWT_SECRET` (base64 of at least 32 random bytes) with no defaults; startup fails without them. Optional: `BOOKWORM_DB_URL` (default `jdbc:postgresql://127.0.0.1:5432/bookworm_db`), `BOOKWORM_TEST_DB_URL` (default database `bookworm_test`), `BOOKWORM_ADMIN_EMAIL` + `BOOKWORM_ADMIN_PASSWORD` (bootstrap admin, created only when both are set). Tests need only the DB variables: they generate their own JWT secret and force the admin variables empty.
- Integration tests use the real PostgreSQL `bookworm_test` DB (no H2, no Docker/Testcontainers on this machine). Never run them against `bookworm_db`.
- Local PostgreSQL 18 is started manually (no Windows service); `pg_hba` uses `scram-sha-256` so a password is always required.
- Database state: `bookworm_db` and `bookworm_test` both exist. Flyway is at V2 in `bookworm_db` (also holds the dev seed: 31 books incl. 1 inactive, 24 authors, 6 categories, and `pg_trgm`); V3 (`users`) and V4 (Phase 3 catalogue constraints) are applied to `bookworm_test` and reach `bookworm_db` on the next normal app start (`bookworm_db` was inspected read-only before V4: no duplicate names, all 31 ISBNs canonical ISBN-13). `bookworm_test` must be left with 0 rows. NEVER create, rename, drop or alter a database or role without the user's explicit approval; only the app's own Flyway migrations may change schema, and only in the phases the user has approved. Do not start the app against `bookworm_db` without asking.
- The app currently connects as the `postgres` superuser. This is acceptable only for local development. Before any shared deployment create a least-privilege application role (not done; needs the user's approval).
- Catalogue integration tests (`CatalogueIT`) insert fixtures with JDBC inside a `@Transactional` test so everything rolls back. Use unusual fixture names/ISBNs (`978999...`, `It ...`) so they cannot clash with seed data, and never commit fixtures.
- Auth integration tests extend `auth/AbstractAuthIT`, are NOT transactional (logins and lockout commit), use the `itauth-` email prefix and delete those rows before and after each test. Never leave rows in `users`.
- Never put credentials in files, chat or commits. `.gitignore` is protected from the file-write tool; edit it via shell.

## Non-obvious Boot 4 facts
- Starters/test packages were renamed: use `spring-boot-starter-webmvc` (not `-web`), `spring-boot-starter-flyway` plus `flyway-database-postgresql`, and test imports `org.springframework.boot.webmvc.test.autoconfigure.{WebMvcTest,AutoConfigureMockMvc}`.
- JWT: use Spring Security's Nimbus resource-server support, not `jjwt` (jjwt targets Jackson 2; Boot 4 uses Jackson 3). Nimbus stays at the Spring Security-managed 10.9.1; do not override to 10.10 without a compatibility/security review.
- Spring 7 no longer treats a bare `@RequestMapping` class as a handler: test controllers need `@RestController`.
- `@WebMvcTest` slices skip `@Configuration` classes. Slice tests must use `testsupport/WebSliceSecurity` (loads the security chain) plus `@MockitoBean` for `UserService` and `JwtDecoder`.
- Nimbus will not sign HS512 with the 48-byte test key; `JwtSecurityIT` hand-builds that token with `javax.crypto.Mac`. `Jwt.getIssuer()` throws for a non-URL issuer (`bookworm`), so read `getClaimAsString("iss")`.
- pom.xml wires the Mockito jar as a `-javaagent` for Surefire/Failsafe to avoid the JDK self-attach warning; keep it when editing plugins.

## Conventions in this repo
- Package-by-feature under `com.bookworm` (`common`, later `auth`, `user`, `catalogue`, `cart`, `wishlist`, `order`, `payment`, `loyalty`). Controllers -> services -> repositories; features talk through services only. Entities never leave the service layer; use record DTOs and hand-written mappers (no Lombok/MapStruct).
- Errors: throw `ApiException(ErrorCode, message)`; `GlobalExceptionHandler` (`common/error`) emits RFC 9457 `ProblemDetail` with stable `code` and `traceId`. Add new codes to `ErrorCode`. Messages in `ApiException` go to clients: never include internals.
- `TraceIdFilter` generates the trace id server-side (client-supplied ids are ignored on purpose).
- Schema only via Flyway (`db/migration`, `ddl-auto=validate`). Dev seed is `db/seed/R__seed_catalogue.sql`: insert-only with `ON CONFLICT DO NOTHING`, never UPDATE/DELETE, loaded only by `application-dev.yml` (which must list BOTH `db/migration` and `db/seed`). Seed ISBNs are synthetic (`978000000NNNC`). Changing the seed file's content makes Flyway re-run it, so keep it idempotent.
- Public catalogue entities (`Book`, `Author`, `Category`) stay `@Immutable` read-only mappings; do not change them. Phase 3 writes go through separate admin entities (`AdminBook`, `AdminAuthor`, `AdminCategory`) on the same tables; `AdminBook.stockQuantity` is `insertable=false, updatable=false` with no setter, so no Phase 3 code may write stock. Search uses `LikePatterns.containsIgnoreCase` (escapes `%`, `_`, `\`) against `lower(col)` to hit the trigram indexes; empty-string (not null) means "no filter" in `BookRepository.search` because PostgreSQL cannot infer the type of a null parameter.
- Public responses expose `inStock` only, never `stockQuantity`, `active` or `version`. Inactive books return 404 / are excluded everywhere.
- Mockito: stub a mock's return value from other mocks only after building those mocks (nested `when(...)` inside `thenReturn(...)` raises `UnfinishedStubbingException`).
- Money is `BigDecimal` / `NUMERIC(12,2)`, INR, `HALF_UP`. Server binds to `127.0.0.1`. Swagger/api-docs are off by default and enabled only by the `dev`/`test` profiles.

## Security rules that apply to all code here
- Secrets via environment only; never bind to `0.0.0.0`; parameterized queries; validate all input server-side; generic client errors, details logged server-side; never log passwords/tokens/PII/payment data.
- Passwords: BCrypt. Container images (if added): `registry.redhat.io` minimal UBI, non-root.
- Auth design (chosen by the user): self-contained Spring Security + JWT + BCrypt, no Keycloak/IdP. This deviates from the global SAML/OIDC rule and is NOT an approved exception; do not describe it as approved. Limitations are listed in `docs/DESIGN.md` section 7. Do not add an external IdP.
- Auth mechanics (`common/security`, `auth`, `user`): HS256 JWT, 60 min, claims `sub`,`role`,`iss=bookworm`,`iat`,`exp`. `CurrentUserJwtConverter` reloads the user on EVERY request, so a deleted/disabled user is rejected and the authority comes from the current DB role (not the token claim). Password change does not revoke tokens. Wrong email, wrong password and disabled account all return the same 401 `INVALID_CREDENTIALS`. Lockout: 5 failures / 15 min via atomic update in `REQUIRES_NEW` (`LoginAttemptService`). BCrypt strength is 12 (4 in tests). Passwords: >= 12 chars, <= 72 UTF-8 bytes. Emails are lower-cased (`Emails`); the DB CHECK enforces it.
- `AdminBootstrap` must never promote an existing account or overwrite its credentials, and must never log credentials (`insertAdminIfAbsent` uses `ON CONFLICT (email) DO NOTHING`).
- `/me/**` derives the user only from the token; `/api/v1/admin/**` requires ADMIN; unknown paths return 401 for anonymous callers (not 404). New public endpoints must be added explicitly to `SecurityConfig` (deny by default).
- Design (entities, checkout/stock/idempotency, loyalty maths, API, phase plan) is in `docs/DESIGN.md`; follow it and stop for user review after each phase. Phase 2 (auth: register, login, `/me`, change password, lockout, admin bootstrap) is committed. Phase 3 (admin catalogue: create/read/update books, categories, authors; activate/deactivate; V4) is committed and pushed (`32d0d59`): no DELETE endpoints, no stock endpoint, new books are inactive, ISBN stored as canonical ISBN-13, unknown JSON fields rejected on admin DTOs via `StrictRequest` plus a Jackson `DeserializationProblemHandler`. Phase 2 findings M1-M3 and L1-L11 in `docs/DESIGN.md` remain open and unchanged.
- Phase 4 (shopping cart and wishlist; addresses moved to Phase 5, Phase 6 unassigned) has an owner-approved DESIGN ("Phase 4 scope" in `docs/DESIGN.md` section 8). No application code or test is implemented. Milestone M1 created `src/main/resources/db/migration/V5__cart_and_wishlist.sql` (file creation only, awaiting owner review and acceptance): it has NOT been executed, NOT been applied to `bookworm_db` or `bookworm_test`, and has not been tested against PostgreSQL or validated against Hibernate. Constraints for that phase:
  - Access and data rules: `/api/v1/me/cart/**` and `/api/v1/me/wishlist/**` are CUSTOMER-only (ADMIN gets 403; add explicit matchers in `SecurityConfig`). Cart and wishlist code must never write `books` or stock and must not import `AdminBook`/`Admin*`. Cart responses never expose the stock count.
  - Inactive books: entries already in a cart or wishlist are shown as `bookId` + `title` + `UNAVAILABLE` only. A POST-add of an inactive book is 404 `NOT_FOUND` even if the caller already holds it; `PUT` on an existing cart line for it is 409 `BOOK_UNAVAILABLE`; both are approved, do not align them.
  - Ownership and DELETE: `PUT` and both moves look the line or entry up in the caller's own cart or wishlist first (404 when absent, in either move direction). All `DELETE` calls are idempotent and never 404. Cart DELETEs return 200 with the updated cart; the wishlist DELETE returns 204 with no body (intentional). An unsupported wishlist `sort` is 400 `VALIDATION_FAILED`.
  - Lock hierarchy: cart row lock first, then the user-scoped wishlist advisory lock, for both moves; a plain wishlist add takes only the advisory lock and never the cart lock.
  - Jackson and errors: no global Jackson coercion change (use feature-local validation, and stop and ask if a global change seems needed). Map only `PessimisticLockingFailureException` to 409 `CONCURRENT_UPDATE`, and only after a test verifies the real Hibernate/PostgreSQL behaviour.
  - Migration approvals are separate: creating V5 needed the owner's explicit approval of the SQL (given; the file exists); reviewing or accepting the file is a further step; applying V5 to `bookworm_test` needs a separate explicit approval, and any run that starts the Spring context (`mvn verify`, `-Dit.test`, `spring-boot:run`) applies it. Approving, creating or accepting the file is not approving its execution; running tests and starting the app are also separate gates. Do not edit V5 once it has been applied anywhere (Flyway checksum).
  - Databases: `bookworm_db` is never accessed or modified (no connection, no read-only query, no app start) during Phase 4 implementation and testing; integration tests use `bookworm_test` only and leave 0 rows. New tests use `itcart-` users and `978998...` ISBNs (the admin ITs own `978999...`).
  - Test execution is gated per milestone: no test run (unit, slice, integration, spike, `mvn verify`) without the owner's prior authorisation for that milestone. Documentation work and verification never run tests, start the app or touch a database.
  - Git: never stage, commit or push without a separate explicit owner approval for that action.
  - Secrets: never print, expose, copy, log or disclose credentials, database passwords, JWT secrets, tokens or other secrets; use the existing environment variables; never ask the owner to paste a secret into a prompt, report or chat.
